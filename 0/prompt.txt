# 実装依頼

## 依頼

orca-env-devsy の relay 環境同期を修正し、Orca Server だけでなく、同じ Orca プロファイルで稼働する daemon が古い relay instance を保持している場合も復旧する。

## 目的

手動 restart や自動再接続後に、Server が新しい relay を参照していても、daemon 経由で開いたターミナルが古い relay を参照し続ける問題を解消する。

## 成功条件

- 接続復旧時と定期 readiness 確認時に、対象 Server と、存在する対象 daemon の `DEVSY_GH_INSTANCE` を、それぞれ現在の relay の `/ready` が返す `instance` と比較する。
- いずれかの非空の instance が relay と異なる場合、対象 Server を先に停止し、対象 daemon が存在すれば停止してから Server を起動する。
- 起動後に Server と、存在する daemon の環境を再確認する。操作中に relay が変わった場合や、必要な対象・環境を確認できない場合は成功とせず、理由を記録して間隔を空けて自動再試行する。
- 対象 daemon が確実に存在しない場合は、daemon の再起動対象なしとして扱う。不在自体を失敗条件にしない。
- Server または daemon の instance が空・未設定なら、そのプロセスについて instance 比較による再起動は行わない。環境を読み取れない場合とは区別する。
- 復旧や再試行の対象、結果、失敗理由を既存の進捗表示と診断記録から追える。
- 利用者の GitHub forwarding 設定や Devsy が報告する利用可能性、ホストの GitHub ログイン状態に介入しない。

## 決定事項

- Server と daemon の実プロセス環境を、それぞれ relay の `/ready` と比較する。
  - 理由: Server 再起動後も daemon は生存し、新しいターミナルに古い環境を渡し得る。adapter の記録では実プロセスの状態を保証できない。
  - 主な棄却案: Server の環境だけを確認する方法。今回の `glaze-ferret-j3` で、Server は一致していたが daemon は古い instance を保持していた。
- Server または daemon の不一致時は、Server を先に停止し、daemon を停止してから Server を起動する。
  - 理由: 動作中の Server による daemon 再起動と adapter の復旧処理との競合を避け、起動後に両者を確認する経路を揃える。
  - 主な棄却案: Server が一致している場合は daemon だけを停止する方法。Orca 側の再起動・引き継ぎとの競合を別途扱う必要がある。
- 不一致時は直ちに自動復旧し、既存ターミナルや daemon が管理する実行中の agent 処理の中断を許容する。
  - 理由: 古い relay 環境を保持したままでは、期待された relay を使えない。
  - 主な棄却案: セッションが終了するまで復旧を延期する方法。
- daemon の特定には Orca プロファイルの PID 情報とプロセスの所有・同一性確認を使う。所有を証明できなければ停止せず、失敗として再試行する。
  - 理由: 対象外のプロセスを操作せず、現在の Orca に適した復旧を行う。
  - 主な棄却案: 公開された daemon lifecycle 操作だけを使う方法。調査した Orca CLI に該当する操作は確認できなかった。
- 実際の Orca ターミナルでの `gh` 実行は検証に用い、通常の復旧成功条件にはしない。
  - 理由: GitHub forwarding の利用やログイン状態は利用者の選択であり、instance 同期とは別の条件である。
  - 主な棄却案: 毎回 `gh auth status` の成功を要求する方法。

## 制約

- Devsy 本体や `gh` wrapper は変更しない。
- 対象 Server と daemon の所有・同一性を停止直前にも確認し、無関係なプロセスや workspace を操作しない。
- 秘密情報を raw または復元可能な形で表示・記録しない。
- 対象 daemon の不在と、存在・所有・環境を確認できない状態を区別する。
- 実環境での中断を伴う検証は承認された対象と範囲に限る。`glaze-hare-3k` を対象にした試験は承認済みだが、共有 supervisor の停止など、他 workspace に影響する操作はその承認に含めない。

## 対象外

- SSH 接続失敗の根本原因修正。
- GitHub 認証や forwarding 設定の変更。
- relay instance の不一致と無関係な Orca daemon の修復。

## 未検証の前提

- 対象環境と Orca の各バージョンで、プロファイル内の PID 情報と実プロセスから daemon の所有・同一性を安全に確認できること。
- Server と daemon の停止後に Server を起動すると、必要な daemon が現在の relay 環境で起動し、ターミナルを利用できること。
- 復旧、定期確認、Server 更新と Orca 側の daemon lifecycle が同時に動く場合にも、対象確認と排他が成立すること。

## 実装時の指示

- 既存の Server 更新・relay 同期の対象確認、停止・起動、排他、再試行、診断の仕組みを調べて適切に再利用する。daemon の PID 形式やバージョンを固定的に仮定しない。
- `glaze-ferret-j3` で観測された「Server は一致、daemon は不一致」を含め、両者の一致・不一致・空・未設定・読み取り不能、daemon の確実な不在、対象の曖昧さを検証する。
- 停止前の対象再確認、停止・起動失敗、起動後の再比較、操作中の relay 変更、並行処理、自動再接続、手動 restart、定期確認の経路を検証する。
- 承認された実環境で検証できる範囲を確認し、Orca から新しく開いたターミナルでの動作と、実行できなかった検証を区別して報告する。
