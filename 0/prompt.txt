# 実装依頼

## 依頼
orca-env-devsy の relay 復旧と Orca Server の環境同期を修正し、`recover` / `restart` の対象別の進捗とエラー表示を改善する。

## 目的
- 手動 restart や自動再接続で Devsy credentials server の instance が変わっても、Orca Server とその後のターミナルが古い relay を参照し続けないようにする。
- 利用者が、どの workspace の処理が成功・失敗し、何が問題だったか判断できるようにする。

## 成功条件
- 接続復旧時と定期 readiness 確認時に、稼働中の対象 Orca Server が保持する `DEVSY_GH_INSTANCE` と現在の relay の `instance` を比較する。
- 両者が異なる場合、対象 Server を再起動し、起動後に現在の relay と一致することを確認する。手動 restart と自動再接続の両方で同じ条件を満たす。
- Server 側の instance が空または未設定の場合、instance 比較による再起動を行わない。Server の特定や環境の読み取りができない場合は、復旧成功としない。
- 再起動や確認に失敗した場合は理由を記録し、状態を確認し直して間隔を空けて自動再試行する。操作の途中に relay が再び変わった場合も、成功とせず再試行する。
- `recover` / `restart` で、各 workspace の対象名、処理結果、失敗理由が分かる。自動再接続と Server 再起動の結果も診断記録から追える。
- SSH 接続が再試行後にタイムアウトした場合、取得できる最後の SSH 失敗内容を秘密情報をマスクして表示・記録する。取得できなければそのことを明示する。
- 利用者が設定した GitHub forwarding の有効・無効や Devsy が報告する利用可能性に、今回の変更が介入しない。

## 決定事項
- 比較には、実行中の対象 Server プロセスの環境と relay の `/ready` を使う。
  - 理由: adapter の再起動や既存 Server の引き継ぎ後も、実際に Server が保持する値を確認できる。
  - 主な棄却案: adapter に起動時の instance を保存する方法。記録の欠落や実プロセスとの不一致を別途扱う必要がある。
- instance の不一致を確認した場合だけ対象 Server を再起動する。
  - 理由: relay の再接続だけでは instance が必ず変わるとは限らず、不要なターミナル切断を避けられる。
  - 主な棄却案: 再接続のたびに Server を再起動する方法。
- Server 再起動に伴う既存ターミナルの切断を許容する。
  - 理由: 古い relay 環境を保持する Server を使い続けても、期待された relay を利用できない。
  - 主な棄却案: 既存ターミナルを維持するため、使えない Server を再利用し続ける方法。
- 失敗時は自動再試行し、復旧を確認するまで成功扱いにしない。
  - 理由: 自動再接続後の一時的な失敗を手動復旧へ戻さずに済む。
  - 主な棄却案: 失敗時に自動再試行を止め、利用者の restart を待つ方法。
- 表示改善は instance 不一致に限らず、`recover` / `restart` の対象別結果と SSH 失敗理由を含める。
  - 理由: 並列処理では対象と失敗原因が対応しないと利用者が判断できない。
  - 主な棄却案: 今回の Server 再起動に関する表示だけを追加する方法。

## 制約
- Devsy 本体は変更せず、adapter 側で対応する。
- instance 不一致への対応に限定し、GitHub forwarding を有効化したり、利用可能性やホストのログイン状態を新たな成功条件にしたりしない。
- 対象 Server の所有を確認し、無関係な Server や workspace を操作しない。
- 秘密情報を raw または復元可能な形で表示・記録しない。
- 実環境での破壊的・中断を伴う検証は、適用される authority の範囲で行う。

## 対象外
- SSH 接続失敗の根本原因の修正。
- Devsy の `gh` wrapper の変更。
- GitHub 認証の設定変更や、ホストのログイン状態の修復。

## 未検証の前提
- 対象環境で、既存の Server 更新処理と同様にポート所有者を一意に特定し、そのプロセス環境を読み取れること。`glaze-hare-3k` では対象 Server の特定と instance 不一致を観測済みだが、他環境では未確認。
- 新しい SSH セッションから Server を起動した際に、その Server が現在の relay instance を受け取ることと、Server 再起動後のターミナル・接続の挙動。
- 同時実行される復旧、定期確認、Server 更新との排他および再試行が、実際の呼び出し経路で成立すること。

## 実装時の指示
- 既存の Server 更新処理の対象プロセス確認と停止・起動の仕組みを調べ、適切な範囲で再利用する。
- 比較、停止前の対象確認、起動後の再比較、およびその間の relay 変更を含む失敗経路を検証する。
- Server の instance が一致、不一致、空・未設定、読み取り不能の場合と、定期確認・自動再接続・手動 restart の経路を検証する。
- 対象別の進捗と失敗表示、SSH エラーの取得不能、秘密情報を含む標準エラーのマスクを検証する。
