# 実装依頼

## 依頼

稼働中の Devsy workspace にインストール済みの Orca Server を、実行中の host Orca Desktop と同じバージョンへ明示的に更新する CLI 操作を実装する。

## 目的

- Desktop と remote Server のバージョン差によって接続できなくなった場合に、既存 workspace の Server を更新できるようにする。

## 成功条件

- 個別更新では provider と workspace ID を指定して対象を一意に選べる。
- 一括更新では provider を省略すると全 provider、指定するとその provider の対象を処理する。
- 停止中の workspace は起動せず、未更新として報告する。
- 一括更新では各対象の失敗後も残りを処理し、対象ごとの結果と全体の失敗を報告する。
- 更新後の Server が Desktop と同じバージョンであり、WebSocket 接続が成立することを確認する。

## 決定事項

- 更新はユーザーが CLI から明示的に開始する。実行中の処理があっても Server を切り替える。
  - 理由: 通常の resume や復旧で予期せず Server を入れ替えず、更新指示を再起動とその影響の承認として扱うため。
  - 主な棄却案: resume 時または互換性問題の検出時に自動更新する案。予期しない中断を伴うため。
- 実行中の host Orca Desktop と同じバージョンを選ぶ。特定または取得できない場合は、切り替えずに失敗を報告する。
  - 理由: Desktop と Server のバージョン差を解消するため。
  - 主な棄却案: 常に最新 stable を選ぶ案。Desktop と一致する保証がないため。
- ダウングレードは通常拒否し、明示的な強制オプションがある場合のみ許可する。
  - 理由: 保存データの後方互換性を確認できない場合があるため。
  - 主な棄却案: 常にダウングレードを許可する案。意図しないデータ互換性の問題を避けるため。
- 切り替え後の起動に失敗した場合、以前の Server の実行ファイルを保持し、自動再起動・自動復旧を抑止する。更新コマンドの再実行では目標バージョンへの更新を再試行する。
  - 理由: 新しい Server が保存データを変更した可能性がある状態で、以前のバージョンを自動起動しないため。
  - 主な棄却案: 以前の Server を自動的に再起動する案。保存データの互換性を保証できないため。
- 成功確認はバージョン一致と WebSocket 接続成立までとする。
  - 理由: 更新後の Server の起動と接続可能性を確認するため。
  - 主な棄却案: 認証付き要求・応答や Desktop 自体の再接続までを成功条件とする案。今回の確認範囲を接続成立までに絞るため。

## 制約

- 通常の resume・復旧では Server を更新しない。
- 停止中の workspace を更新のために起動しない。
- workspace の識別情報を確認し、置き換えられた workspace を更新しない。
- pairing 情報や credential を出力・記録しない。

## 対象外

- Desktop 側の pairing 認証や実際の再接続の確認。
- Desktop の接続情報の自動更新。
- 初回インストールのバージョン選択方針の変更。
- 保存データの自動復元。

## 未検証の前提

- 既存の host Orca 検出経路で特定した resources から、更新対象に使える Desktop のバージョンを取得できること。
- Desktop と同じバージョンの公式 Linux asset を remote の対象 architecture 向けに取得できること。
- Server の安全な停止、切り替え、起動失敗時の自動復旧抑止を、既存の接続管理と競合せずに実現できること。

## 実装時の指示

- 既存の host Orca 検出、workspace 識別、接続管理および一括操作の実装を確認して活用する。
- 更新後の WebSocket 接続成立は、Desktop の認証や再接続を保証するものとして扱わない。
- 失敗時に保持した以前の実行ファイルと再試行に必要な状態を維持する。
