# 実装依頼

## 依頼
`orca-env-devsy` の新規 `orca-worktree` 環境で、shallow clone 後に `origin` の全ブランチの追跡 ref と先頭 commit を軽量に初期化し、Orca が GitHub PR から worktree を作成できるようにする。

## 目的
- Dev Container 作成時の追加通信を抑えつつ、PR の開始 commit と upstream の不足による worktree 作成失敗を解消する。
- 利用者の Git 操作は、利用者自身の設定を尊重した通常の挙動にする。

## 成功条件
- 新規 `orca-worktree` 環境で、shallow clone 後に `origin` のブランチ追跡 ref を初期化できる。
- 初期取得では `--depth=1 --filter=tree:0` を使い、tree と blob は必要時に Git が取得できる。
- 対象ブランチを upstream として設定できる。
- 利用者の通常の `git fetch` に adapter がフィルターを強制しない。利用者の明示設定は尊重する。
- 初期化が失敗した場合は環境作成を失敗させ、失敗した段階と原因を識別できる。
- 非 shallow リポジトリの既存履歴を、この対応によって shallow にしない。
- 既存環境の再開時には、この初期化を追加実行しない。

## 決定事項
- 新規 `orca-worktree` 環境では、この対応を既定で有効にする。
  - 理由: Orca の通常操作を成立させるために必要な初期化である。
  - 主な棄却案: recipe ごとの opt-in。通常操作を使うための追加設定が必要になる。

- shallow clone 後、全ブランチの先頭 commit を `tree:0` で取得する。
  - 理由: master の作成時にも追加される通信を小さく保つ。
  - 主な棄却案: `blob:none` で全ブランチの tree も初期取得する。Glaze の Mac からの単発測定では、ローカル Git オブジェクト領域の増分が約 1.75 MB だった。

- 不足オブジェクトを Server 外の Git からも取得できるよう、必要な promisor 設定と fetch refspec をリポジトリの Git config に設定する。
  - 理由: Server の環境変数だけでは、それを継承しない Git が不足オブジェクトを取得できない。
  - 主な棄却案: Server の環境変数だけで設定する。別の環境からの Git 操作が失敗し得る。

- 初期化用のフィルターを後続の通常 fetch に強制しない。明示的な既存設定は尊重する。
  - 理由: 今回制御したいのは adapter と Orca の初期化であり、利用者の Git 設定を黙って上書きしない。
  - 主な棄却案: `blob:none` または `tree:0` を後続 fetch の既定として強制する。

- 追加 fetch は既存の接続準備期限を共有し、専用の２秒タイムアウトは設けない。
  - 理由: ２秒・100 KB は Glaze の Mac からの単発測定に基づく目安であり、固定上限にはしない。
  - 主な棄却案: ２秒で失敗させる。通信の揺れで環境作成が失敗しやすい。

- サーバーがフィルターに未対応の場合は Git 標準のフォールバックに任せる。
  - 理由: 事前確認の通信と独自のプロトコル解析を追加しない。
  - 主な棄却案: フィルター対応を別通信で事前確認してから fetch する。

## 制約
- Orca 本体を変更しない。
- Git ラッパーや定期的な全ブランチ更新を追加しない。
- 利用者の明示的な Git 設定や Server 環境変数を黙って上書き・削除しない。初期化に必要な条件と両立できない場合は理由を示して失敗する。
- 以前案内した `GIT_CONFIG_*` による `blob:none` 設定が残っている場合、その明示設定は優先される。自動削除せず、必要に応じて利用者へ伝える。
- フィルター未対応時には Git が tree や blob も取得し、通信量・時間が増え得ることを許容する。

## 対象外
- 既存環境の再開時の自動初期化。
- 利用者の Git コマンドに対するフィルターの強制。
- ２秒または 100 KB の固定上限の実装。

## 未検証の前提
- 実際の対象 VM における Git のバージョン、認証 relay、初期化時間と通信量。約 1.65 秒・83 KB は Mac から Glaze のリモートを測定した際の、ローカル Git オブジェクト領域の増分であり、VM の通信量ではない。
- VM 内でも、promisor 設定と空の `remote.origin.partialclonefilter` によって、通常 fetch がフィルターなしとなり、不足オブジェクトを必要時に取得できること。Git 2.54・2.55 のローカル検証では確認済み。

## 実装時の指示
- Devsy の workspace 作成後、認証 relay を利用できる状態にしてから初期化し、Orca Server が worktree を作る前に完了させる。
- `origin` の全ブランチに対応する fetch refspec を設定し、既存の明示設定との競合を扱う。タグやサブモジュールの不要な取得は行わない。
- 通常の Git はフィルター未設定が既定である点に注意する。ローカル検証では、`remote.origin.partialclonefilter` が未設定だと、遅延取得時に Git 自身が `blob:none` を保存する場合があった。明示的な利用者設定を尊重しつつ、フィルターを強制しない構成を検証する。
- 初期化のタイムアウトを SSH・relay の失敗と誤認させず、fetch の段階と原因を診断できるようにする。フィルター未対応による Git の警告も把握できるようにする。
- 通常の shallow 作成、PR head の取得と upstream 設定、利用者 Git の通常 fetch、不足オブジェクトの遅延取得、フィルター未対応、既存設定との競合、非 shallow リポジトリ、失敗時の扱いを検証する。
- VM での検証ができない場合は、ローカル検証と分けて未確認範囲を報告する。
