# 実装依頼

## 依頼
共有 supervisor の異常終了後の復旧、引数なし `restart` による supervisor の入れ替え、および SSH 制御ソケットの配置と消失からの復旧を実装する。

## 目的
- supervisor が異常終了しても、明示的な復旧操作により workspace ごとの元の実行環境で管理を再開できるようにする。
- 引数なしの `restart` で共有 supervisor を確実に起動し直し、対象の接続を再作成できるようにする。
- SSH 制御ソケットのディレクトリが消失しても復旧でき、失敗時には原因を診断できるようにする。

## 成功条件
- workspace ごとの実行環境全体が復旧可能に保存され、supervisor の異常終了後も使用される。
- workspace 単位の登録はその workspace の保存環境を更新する。一括 `recover`・`restart` は呼び出し元の環境で各 workspace の保存環境を上書きしない。
- `recipe recover` は指定 workspace を復旧し、一括 `recover` は保存済みの対象 workspace を復旧する。起動した supervisor は管理対象 transport の後始末も引き継ぐ。
- 引数なしの `restart` は毎回共有 supervisor を終了してから新しい supervisor を起動し、稼働中の全対象 workspace の接続を再作成する。停止中の workspace は起動せず、スキップを報告する。
- 一部の workspace の再接続が失敗しても残りを試み、成功した接続を維持する。失敗対象を報告し、コマンド全体は失敗とする。
- SSH 制御ソケット用ディレクトリの消失後、実際の接続経路で再作成と復旧を試みる。復旧できない場合は原因を診断できる。
- 保存環境、接続、transport の所有権および cleanup が、異常終了、再試行、同時操作、workspace の管理終了を通じて整合する。

## 決定事項
- workspace ごとの実行環境全体を、秘密値を含めて adapter の状態ディレクトリに保存する。所有ユーザーだけがアクセスできる権限を設定する。
  - 理由: 異常終了後も workspace ごとの接続先や認証条件を復元する必要がある。
  - 主な棄却案: 呼び出し元の環境で代用する案は、workspace ごとの環境を再現できない。
- 保存環境は workspace 単位の登録時に更新し、一括操作では保存値を使用する。
  - 理由: 環境変更を反映しつつ、異なる workspace の環境を混同しない。
  - 主な棄却案: 初回の環境を固定する案は、後の環境変更を反映できない。
- 保存環境は停止中も保持し、workspace の削除または adapter による管理終了が完了したら削除する。
  - 理由: 停止後の再開に必要な情報を保持し、管理終了後は残さない。
  - 主な棄却案: 停止時に削除する案は、再開時に環境の再登録を要する。
- supervisor の異常終了後は、明示的な `recover` または `restart` を契機に復旧する。
  - 理由: 常時監視や自動再起動は求めない。
  - 主な棄却案: 別の常駐監視プロセスや OS サービスによる自動復旧。
- 引数なしの `restart` は毎回 supervisor を入れ替える。`recipe restart` は対象 workspace の接続だけを再作成し、共有 supervisor を入れ替えない。
  - 理由: 一括操作は共有 supervisor を含む破壊的な再起動とし、workspace 単位の操作範囲は維持する。
  - 主な棄却案: バージョンが異なる場合だけ入れ替える案、および `recipe restart` でも共有 supervisor を入れ替える案。
- 一括 `restart` では旧 supervisor を終了してから新 supervisor を起動する。SSH セッションの切断を許容し、切断された利用者側セッションは必要に応じて再接続する。
  - 理由: `restart` は破壊的操作とする。
  - 主な棄却案: 新 supervisor の準備完了まで旧 supervisor と接続を維持する案。
- 停止中の workspace は一括 `restart` で起動せず、スキップを報告する。
  - 理由: 従来の復旧動作を維持し、意図しない workspace 起動を避ける。
  - 主な棄却案: 停止中の workspace を起動する案、およびスキップ自体を失敗とする案。
- SSH ソケットの配置には Linux の `XDG_RUNTIME_DIR` と macOS の適切なユーザー用ディレクトリを優先し、使えない場合は `/tmp` を含む短い場所へ fallback する。いずれも adapter 所有と分かるパスを使う。
  - 理由: runtime ファイルに適した配置先を優先しながら、未設定やソケットのパス長制約に対応する。
  - 主な棄却案: 推奨配置先が使えない場合に接続を失敗させる案。

## 制約
- 実行環境に含まれる秘密値を診断ログやエラー出力に漏らさない。保存時の権限、所有権、更新の原子性、削除および失敗時の扱いを設計する。
- 一括 `restart` は管理対象 transport と実行中の SSH セッションを切断し得る。新 supervisor の起動に失敗した場合はエラーを報告し、利用者が復旧する。
- ソケット配置先は所有権・権限を検証し、実際の SSH ソケットパス長を考慮する。ディレクトリの消失を配置先の寿命保証だけに依存せず扱う。
- 停止中の workspace を一括 `restart` によって起動しない。

## 対象外
- 既存の稼働中 supervisor との互換性や引き継ぎ、および旧契約からの移行。
- supervisor 異常終了時の自動検知・自動復旧。

## 未検証の前提
- 実環境で発生した `/tmp/oe...` の消失理由。稼働中の supervisor が再接続を繰り返していたが、ソケットディレクトリの消失と supervisor のバージョン差との因果関係は確定していない。
- macOS で利用可能なユーザー用ディレクトリの寿命と、対象 SSH 実装で許容されるソケットパス長。

## 実装時の指示
- ソケットディレクトリ消失の失敗条件を調査し、配置変更だけで問題が解決すると決め打ちしない。稼働中 supervisor の再接続経路と、保存済み状態からの復旧経路を検証する。
- supervisor 異常終了後の復旧、workspace ごとに異なる環境の保持・更新、一括 `restart` の部分失敗、停止中 workspace のスキップ、transport の後始末を検証する。
